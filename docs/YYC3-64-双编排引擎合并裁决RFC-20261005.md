# RFC：conductor / orchestrator 双编排引擎合并裁决

## 一、现状（首审 04 号 §四 + archive 仓实态）

| 维度 | conductor | orchestrator |
| ---- | --------- | ------------ |
| 形态 | TS DAG 流水线引擎（原型，skillId 分支显式抛错） | TS 调度器（scheduler+decomposer，src/ 真实实现） |
| 成熟度 | 14 用例；**skillId 未接通**（README 自认） | 39 用例；LLM 分解策略调用即 throw（自认桩） |
| 定位重叠 | 两包 README 均自认「职责重叠，整合方案讨论中」 | 同左 |
| 生产关联 | 均未进入生产链（生产编排=components/ai_family_orchestrator.py，Python） | 同左 |

**问题**：双轨并存使「改哪份」长期模糊（与 Agent 三拷贝漂移同构的架构级隐患）。

## 二、裁决选项

| 选项 | 方案 | 优 | 劣 | 建议 |
| ---- | ---- | -- | -- | ---- |
| **A** | 保留 orchestrator，conductor 降级「DAG 声明格式参考」 | 命中现状（orchestrator 更完整）；改动最小 | conductor 14 用例沉没 | ✅ **推荐** |
| B | 以 conductor 的 DAG 声明式为准，重写 orchestrator 调度核 | 声明式 YAML 与 YYC3-03「六阶段 YAML」愿景契合 | 重写成本高；两包均未生产验证 | 备选 |
| C | 双轨保留，写边界声明 | 零改动 | 债务显性化但未消除（已证漂移代价） | 不推荐 |

## 三、推荐路线（选项 A，两步走）

1. **立即（文档级）**：orchestrator README 升格「编排参考实现」；conductor README 标注「DAG 格式参考·非执行件」+ 顶部 DEPRECATED 指引；`upstreams.tsv` 豁免域同步注记
2. **中期（等触发条件）**：当「六阶段 YAML 声明式编排」真正立项（manju 服务层上线后）——以 conductor 的 PipelineDef 格式为声明层、orchestrator 调度核为执行层合并为新 `orchestration` 包；触发前不投入工程资源

## 四、裁决影响面

- 漫剧生产链零影响（生产编排=Python components，本 RFC 仅涉 TS 参考层）
- 与事实源裁定（core/agents）正交：本 RFC 管「编排引擎」，前者管「Agent 实现」

## 五、待用户裁决

> 请批复：A / B / C（或提出 D）。批复后执行 §三对应步骤并升级本 RFC 为决议版。
