# E2 演进勘察包：H3 协议扩展 + Ref 库建设

## 一、范围与结论速览

| 项 | 对应 | 勘察结论 | 后续动作 |
| - | ---- | -------- | -------- |
| A9 H3 frames2video | OnlyShot 四模视频（首尾帧锁过渡） | **现状无通道**（payload 仅 5 键）；提案已成型，落地需 H3 侧配合 | 提交提案 + 客户端特性探测先行 |
| A8 Ref 库 | OnlyShot 80-150 张工业级 Ref | **现状单图**（hero_base）；五类实体规划已裁剪定稿 | 分三批建设，批一只用现役管线 |
| A10 可观测性 | MiraFrame 进度推送 | 轻量方案定稿（JSONL + SSE） | 低优先，穿插 |
| A11 Provider 体检 | MiraFrame 连接测试 | 复用 G1 三探针模式扩四探针 | 低优先，穿插 |

**红线提醒**：本包为勘察与提案，**不含任何已生效的协议变更**；H3 侧未确认前不得在生产链路引用首尾帧参数。

## 二、H3 frames2video 协议扩展提案

### 2.1 现状链路（以代码为准）

[image_to_video](file:///Users/yanyu/YYC-Cube/YYC3%20AI%20Family-Comic%20Drama/yyc3-ai-agent-archive/components/drama_stage_adapter.py#L505-L525) →
[H3VisionClient.generate_single](file:///Users/yanyu/YYC-Cube/YYC3%20AI%20Family-Comic%20Drama/yyc3-ai-agent-archive/components/drama_stage_adapter.py#L167-L189)：
`POST /api/tasks`，body = `{"task_type": "generate_single", "payload": {...}}`，payload 仅五键：

```text
batch（+ image_ref 实为 H3 批次号，如 "93"）/ seeds / prompt_file / variant / preview
```

结论：**当前链路的"图生视频"实为按批次号的文/图驱动出片，无首帧-末帧插值能力**。OnlyShot 的 frames2video（提供首尾帧锁定镜头过渡）在本项目无对应通道。

### 2.2 能力缺口量化

| 场景 | OnlyShot 模式 | 本项目现状等价 | 缺口影响 |
| ---- | ------------- | -------------- | -------- |
| 常规镜头（约 80%） | image2video | 批次号 + prompt_file ≈ 等价 | 无 |
| 爆点/动作镜头（约 10-15%） | frames2video（首尾帧） | **无等价** | 镜头过渡不稳、爆点表现力受限 |
| 复杂长镜头（约 5%） | multiframe2video | 无等价 | 可用多镜替代（成本换质量） |
| 兜底 | multimodal2video | 多参考图锁定 | 部分等价（Ref 库增强） |

即：**缺口集中在高价值爆点镜头**，与 63 号 A2 节奏地图的 beat 标注（twist/satisfaction 节点）天然对应——首尾帧能力落地后可定向增强这些节点。

### 2.3 提案 A（推荐）：payload 扩展，向后兼容

不新增 task_type，仅在 `generate_single` 的 payload 增可选帧键，**键缺失即退化为现状行为**（零破坏）：

```jsonc
{
  "task_type": "generate_single",
  "payload": {
    "batch": "93",
    "seeds": "42",
    "prompt_file": "…/motion.txt",
    "// 新增（可选）": "",
    "first_frame": "input/shot-EP01-012.png",   // 首帧（相对 H3 input 根）
    "last_frame":  "input/shot-EP01-013.png",   // 末帧（缺省=仅首帧=image2video）
    "interp": "linear",                          // linear|ease（帧间插值曲线）
    "frames": 49                                 // 目标帧数（缺省走 H3 既有档位）
  }
}
```

优点：单点扩展、旧客户端零改动、H3 侧可按帧数分支复用现有 pipeline。
缺点：payload 语义膨胀（5 键 → 9 键），需 H3 侧参数校验。

### 2.4 提案 B（备选）：独立 task_type

新增 `task_type: "generate_frames2video"`，payload 独立演进，语义更干净；代价是 H3 侧需新增任务分支与路由，客户端需按 task_type 分流。**建议作为 A 的中期归宿**：先用 A 快速验证，能力稳定后迁 B。

### 2.5 客户端兼容路径（本项目侧先行，无需等 H3）

可行性关键：**不阻塞在本项目可实现的部分**。落地顺序：

1. **特性探测**：扩展 `H3VisionClient.healthz()`，解析返回的 capabilities（若 H3 提供）→ 新增 `supports_frames2video` 属性；H3 未返回时默认 `False`（保守）。
2. **能力门控调用**：`image_to_video` 增可选 `first_frame`/`last_frame` 参数，仅当 `supports_frames2video` 为真时注入 payload，否则记录 `frames_unsupported` 降级留证并走现状路径。
3. **变通方案（当前可用）**：爆点镜头以「首帧法 + 运动提示词强化」近似——首帧选 anchor_guard 高分镜，prompt_file 内嵌过渡描述（`推镜/环绕/骤停`）。**须在留证中标注 `mode: first_frame_approx`**，不得冒充 frames2video。

### 2.6 落地步骤与风险

| 步 | 动作 | 负责侧 | 验收 |
| -- | ---- | ------ | ---- |
| S1 | 提交提案 A + payload schema 至 H3 维护方 | 本项目 | 提案受理回执 |
| S2 | H3 侧实现帧通道 + capabilities 声明 | H3 | `/api/healthz` 含 capabilities |
| S3 | 客户端特性探测 + 能力门控接入 | 本项目 | 探测为真才注入，为假走降级 |
| S4 | 爆点镜头 A/B 对照（frames2video vs 首帧法） | 本项目 | 过渡稳定性指标 + 人工判 |

风险：① H3 侧排期不可控（→ S3 先行，S1/S2 并行）；② 帧数/分辨率耦合可能触发显存超限（→ 先 512/25 帧小样验证）；③ 首尾帧色调不一致导致闪帧（→ Ref 库同场景多角度图配套，见第三章）。

## 三、Ref 库分批建设方案

### 3.1 现状

- 角色参考：`ComfyUI/input/hero_base.png` **单图**（2026-10-02 起为唯一可信参考系锚点）。
- Delta 评估：单图锚定下 SD15 combo 生产域 mean 0.8672 / min 0.7846；**min 是短板**（最差镜 0.7846 < 0.85 目标）——单图对姿态/表情/角度变化的鲁棒性不足正是 min 低的原因。
- 结论：Ref 库不仅是"对标补齐"，更是**提升 min 指标的可行路径**（多参考 → 多角度评分口径 → 稳定度改善）。

### 3.2 Jellyfish 五类实体模型裁剪适配

Jellyfish 维护角色/演员/场景/道具/服装五类实体。裁剪适配：

| Jellyfish 实体 | 本项目采纳 | 落位 | 说明 |
| -------------- | ---------- | ---- | ---- |
| 角色（character） | ✅ 采纳 | `face_library_sd/{char}/` 扩展 | 现役 feature.npy 单向量 → 多参考图集 |
| 场景（scene） | ✅ 采纳 | 新增 `ref_library/scenes/` | 固定场景关键词 + 多角度图，抑制场景漂移 |
| 道具（prop） | ✅ 采纳（轻量） | 新增 `ref_library/props/` | 关键道具（如朱砂符/玉佩）一致性 |
| 服装（costume） | ⚠️ 并入角色 | 角色目录内 `costume_*` 子目录 | 本剧单一造型，独立建类属过度工程 |
| 演员（actor） | ❌ 不采纳 | — | 本项目为生成角色，无真人演员实体 |

即 **4 类落地、1 类不采纳**（避免为对标而建无用实体）。

### 3.3 分批建设计划

| 批 | 范围 | 图量 | 依赖 | 验收口径 |
| -- | ---- | ---- | ---- | -------- |
| 批一 | 角色动作/表情（sd-hero） | 5-8 张 | 现役 SD15 管线（零新增依赖） | 多参考评分下 min ≥ 0.80（vs 单图基线 0.7846） |
| 批二 | 场景多角度 | 6-10 张 | 批一复用 | 场景漂移人工判 + 关键场景 sim 稳定 |
| 批三 | 道具细节 | 3-5 张 | 与 buffs 二批并行 | 道具镜头一次通过率提升 |
| 联动 | 基模迁移后复用 | — | YYC3-62 阶段 2 | SDXL LoRA 重训时 Ref 库跨基模复用 |

批一**不依赖 H3 协议扩展**，可立即执行——这是本包中优先级最高的可落地项。

### 3.4 与现役链路的联动点

- `AnchorGuard`：多参考 → `pre_anchor`/`post_check` 可用多参考取 **max/mean** 口径（需小改，评估后定）。
- `run_storyboard_candidates.py`：候选预打分可直接消费多参考（多角度评分更稳）。
- H3 frames2video：首尾帧取自同场景多角度图，色调一致性有保障（消解 2.6 风险③）。

### 3.5 成本估算（口径同 61 号目录）

批一 5-8 张 × 1024px 静态图生成，按本机 512px ~8-10s 折算 1024px 约 27s/张（37 轮 G4-006 实测）→ **约 3-4 分钟机器时间，零 API 成本**（自托管）。批二/批三同量级。**总成本可忽略，瓶颈在人工筛选与标注**。
