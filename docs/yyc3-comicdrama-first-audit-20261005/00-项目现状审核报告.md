# 第二部分 · 深度维度分析（穿透式诊断）

## 2.1 架构合理性 ★★★★☆

**现状**：四层架构（业务/编排/底座/硬件）+ 四仓拆分清晰；网关「入口→中间件4件套→11路由→20+服务→ORM」教科书分层；上游池 fnmatch+EWMA+熔断+探活+sovereignty 路由对齐 one-api/litellm 水准；一致性三件套红线纪律（确定性派生/降级留证/escalate 转人工）贯穿。

**问题**：① conductor 与 orchestrator 双编排引擎职责重叠（两包 README 自认"整合方案讨论中"）；② 0379-world 三轨目录并行（core/api 运行时 / app/ 脚手架 / agents/ 孤立脚本），path_normalize 双实现靠注释"逐字对齐"人工同步；③ manju 后端服务层与引擎内核之间"隧道未开凿"（引擎优秀但 0 端点暴露）；④ h3 dashboard(HTML) 与 apps/console 双面板并存。

**影响**：架构设计成熟度显著高于工程化完成度；双引擎/双实现/双面板三处双轨若不裁决，长期改动成本递增；manju 服务化是前后端联调的唯一断点。

## 2.2 代码质量 ★★★★☆（核心）/ ★★☆☆☆（外围）

**现状**：四仓 TODO/FIXME 全零（以 TC-/OBS- 编号体系替代，可追溯）；SQL 全参数化；注释与 docstring 密度高；事故复盘直接转化为代码防线（09-27 僵尸批次→BatchTerminated 优雅终止；09-28 静默成功→exit 1 编排标红；参考系漂移→设定图本体锚定）。前端 TS strict + AbortController 超时 + withFallback 降级封装；SSE 幂等/脏写保护。

**问题**：① 0379-world 限流中间件在 BaseHTTPMiddleware 中 raise HTTPException——实际客户端收到 **500 而非 429**（Starlette 陷阱，`middleware/rate_limit.py:207/221`）；② chat.py 响应缓存 key 不含用户身份（跨用户缓存串扰面）；③ `except Exception: pass` 13 处；main.py 1028 行巨石；④ manju anchor_guard.py:23 类型注解错误（`str = None`）；⑤ agent-archive base_agent Mock 降级**返回值无 degraded 标记**——LLM 故障时九步闭环"假成功"全链跑完，质检对 Mock 文本打分。

**影响**：核心算法与安全防线质量属生产级；但静默失败点（Mock 降级/吞异常/缓存串扰）会在真实生产中制造"看似成功"的脏数据，排障代价高。

## 2.3 技术债务 🔴 高（以"空占位"形态存在）

**现状量化**：manju 34 个 0 字节文件（服务层 21 + deploy 9 + scripts 5）；h3 3 个空文件（sse.py + 两个 configs YAML）+ submodule 未检出 + 白名单 3/5 幽灵脚本；agent-archive 11 个空文件（8 skills.yaml + 2 orchestrator 残留）；0379-world 7 个空文件 + Makefile 15+ 幽灵引用 + requirements.txt 缺失。过时依赖：passlib(停更)×bcrypt5 已知不兼容；datetime.utcnow 弃用遍布 ORM。

**问题**：债务不以注释而以"0 字节承诺"存在——README/Makefile/CHANGELOG 描述的能力与磁盘现实大面积脱节（0379-world CHANGELOG 声称 34 用例实际 2 个；h3 SCRIPT_ALLOWLIST 引用不存在的 pipeline-tools/）。

**影响**：新成员/AI 导师按文档行事必踩空目录；`make install/dev/test` 在 0379-world 全链哑弹；h3 本快照态不可运行（需 submodule init 或补拉清单）。

## 2.4 性能风险 🟡 中

**现状**：DGX 提速 4.75x 已实证（384p 1109s vs Mac 5267s）；热批产 434.4s/镜、13.3s/it；夜批单晚 3 集；成本 0.02–0.03 元/集。GB10 排障链（cu130 wheel/串行化/HF离线变量）已沉淀。

**问题**：① G3-006 单镜 ≤5min 目标实测 1109–1291s（含模型加载），超标 2.2–4.3 倍，仅热批摊薄后接近；② h3_common `vram_limit=96` 硬编码不分端（M4 128G vs GB10 128G 统一内存但预算语义不同）；③ manju episode_planner O(n²) 求和；④ base_agent 同步阻塞 httpx（async 上下文风险）；⑤ n2 DGX 被占，算力单点化 n1——故障域收敛 50% 产能的承诺实际只剩单节点。

**影响**：产能目标（G5 002：3→≥4 集/晚）依赖热批口径成立；算力冗余承诺与 n2 现状不符，夜间批量高峰存在排队风险（37 轮冒烟已现 ComfyUI 队列 300s 超时先例）。

## 2.5 安全风险 🟢 良好（设计）/ 🟡 待收紧（细节）

**现状**：四仓硬编码密钥扫描全零；.env 全 gitignore + example 占位；网关 JWT(HS256+issuer)+X-API-Key 双轨 + VK 三层缓存 + 启动拒绝默认密钥；h3 写操作 fail-closed HMAC claim + 恒时比较 + 脚本白名单 + 零命令拼接；agent-archive SSRF 三道闸（协议/主机白名单/DNS 重解析）+ XFF 跳数模型；SQL 全参数化。

**问题**：① `/metrics` `/docs` `/redoc` `/openapi.json` 免鉴权（公网暴露面）；② WS token 走 URL Query（进代理日志）；③ manju 前端 middleware 缺 CSP；SSE 端点无鉴权预留（EventSource 不支持自定义头）；④ 限流阈值/可信代理 IP 硬编码，X-User-ID 未绑定认证身份；⑤ .env.example 泄露内网 Tailscale 拓扑；patroni.yml 弱占位口令；⑥ JWT 无吊销/jti，RBAC admin 签发为死路径。

**影响**：内网部署下风险可控；一旦按 01 号总纲对公网开放（api.0379.world CORS 已预留），②①⑥将立即成为攻击面；SSE 鉴权方案缺位会在网关鉴权接入时返工。

## 2.6 可维护性 🟡 中

**现状**：文档体系是全项目最强资产——60+ 篇分层文档、HANDOFF 会话日志、TC 用例留证 JSON、attachments 原样归档（含错误参考系 raw 报告"如实保留不删除"的诚实留证文化）；pyrightconfig 按 venv 分流；执行器脚本可复跑（断点续跑/--reuse-existing）。

**问题**：① 文档与现实的"承诺差"（空占位/幽灵引用）反而抬高认知成本；② 测试为脚本式自研框架（非 pytest），sys.exit 会杀死 pytest 收集，CI 无法直接接入；③ G1-005 测试 cwd 相对路径（须从 tests/ 运行，本轮实测证实）；④ 环境复现三重漂移（py3.11 Docker vs py3.14 venv vs 无锁文件）；⑤ 根仓 README 门禁徽章停在 G1，实际已 G4 收割+G5 执行——**主 README 已过时**。

**影响**：AI 跨会话衔接优秀（HANDOFF 机制有效）；但人类新人入职与 CI 化受阻；文档可信度需以 attachments JSON 为准绳二次校验。
