# 第五能力审核论证（2026-09-14，基于全端实勘）

> 审核对象：《MiniMax-H3数字人结构衔接可行性分析》《10-DGX-Spark部署生产运维指南》
> 审核基准：0379-World 09-14 实况锚点（API全链路闭环文档 §十-ter）——公网三能力、上游池机制、Agents 9 容器、双机 GPU 0.8 占用、NAS=Tailscale ~2MB/s。

## 一、总评

**可行性分析"完全可无缝衔接"的方向正确，但有四处需修正后方可执行**。核心分歧不在"能不能衔接"（能），而在**执行顺序与两个架构细节**（同步 API 设计缺陷 + 网络带宽假设错误）。

## 二、四处修正（逐条论证）

### 修正 1：「零算力抢占」成立，但 Mac=主开发机的任务冲突需错峰

- 实况：yyc3-22 是**主开发机**（本会话/部署桥 watch.sh cron */2min/日常 IDE 均在其上），3.2h/条的批量任务白天运行会与开发争内存（96G vram_limit 预留后系统仅余 32G）。
- **采纳**：docs/10 §6.1 已有"22:00 夜间批量 cron"设计——可行性分析应将其升格为**硬约束**：`Phase 2 起所有批量任务走夜间窗口（22:00-08:00）`，白天仅允许单条/少帧冒烟。

### 修正 2：`/v1/video/generate` 同步端点设计**不可行**，改异步任务式 API

- 实况：网关 proxy 层同步转发超时 120s；视频生成单条 1-3 小时——**同步 HTTP 必超时**，且网关现有 capability 机制为"请求-响应"型。
- **修订设计**（第五能力专属，独立于 proxy 同步通道）：

```
POST /v1/video/tasks            # 提交：script/ref_image/params → {task_id, status:"queued"}
GET  /v1/video/tasks/{task_id}  # 轮询：{status: queued|running|scoring|done|failed,
                                #        progress, manifest_uri, video_uri(NAS), scores}
GET  /v1/video/tasks?limit=     # 列表（治理中枢视角）
```

- 实现：NAS 网关新增 `video_tasks.py` 路由 + Redis 任务表；**Mac 侧轻量 runner**（拉队列→调 batch_ref2va_nf4→回写状态/产物 NAS 归档）。Mac↔NAS 走 SSH/rsync（复用部署桥模式）。
- 归档：产物落 NAS `/Volume1/yyc3_hd/video_batchXX/`，manifest.json 双写（本地+NAS）。

### 修正 3：网络带宽描述与实况不符——归档通道是瓶颈

- 可行性分析称"内网万兆对接 NAS"——**实况：Mac↔NAS 仅 Tailscale ~2MB/s**（历史实测，NAS SMB 亦禁用于大文件）。
- 影响：单批产物数百 MB~数 GB，Tailscale 同步将占满夜间窗口。
- **修订**：① 夜间 rsync（压缩+断点续传，rsync -z 实测可提升 3-5 倍有效吞吐）；② 大批量走移动硬盘直拷 NAS（人工兜底）；③ manifest.json（KB 级）实时同步无碍——**"单一事实源实时、媒体文件批量"双速制**。

### 修正 4：Phase 4「DGX 侧部署」当前无窗口，排序让位

- 实况：双机 GPU 0.72(旗舰)+0.08(RAG) 占用；H3 需 ~33G RSS（M4 峰值 32.85G）→ **当前双侧均无余量**；且 GLM 替代路线（AWQ-INT4）排队中。
- docs/10 的"128GB 统一内存"应更正为 **121.69GiB 可用**（128G 标称）；其 NGC 容器/bitsandbytes 验证流程本身严谨 ✓（与 0379-World"官方容器优先"铁律一致）。
- **排序**：DGX 迁移（含 docs/10 §8 验收清单）排在 GLM 线终局之后；届时优先 **Pruned 版**（bf16 直载绕过 bnb 依赖，docs/10 §5.2 判断正确）。

## 三、第五能力 API 衔接规范（对齐 0379-World 契约）

| 项 | 规范 |
| ---- | ------ |
| 认证 | 同现有 X-API-Key/JWT（网关中间件统一，video 路由自动纳入） |
| 响应头 | 任务型无 `X-YYC3-Upstream`（无同步上游）；以 `X-YYC3-Task-Node: mac-yyc3-22` 披露生产节点 |
| 可观测 | task 生命周期事件写 usage_log（复用 log_usage）；治理中枢:25700 收 task 审计 |
| Agent 挂载 | 归属**创想·灵韵**（可行性分析 §3.1 正确 ✓）；灵韵 Agent 增 video_skill（POST 任务+读结果两工具） |
| 测试 | 四层体系纳管：pytest 桩测 task 状态机 → CI → NAS 冒烟（提交假任务全生命周期）→ 公网灰度 |

| Phase | 内容 | 状态/依赖 |

| **2.1 归档通道** | manifest 实时 rsync + 媒体夜间 rsync 双速制；NAS 目录规约 | 立即可做（半天） |
| **2.2 夜间批量** | 22:00 cron + 断点续跑（docs/10 §6.1）+ 次晨报告推送 | 依赖 2.1 |

## 五、结论

**第五能力审核通过（附四处修正）**：立即启动 Phase 2.1 归档通道与 2.2 夜间批量（零风险纯增益）；2.3 异步任务 API 按 §三 规范实施；DGX 迁移挂起待算力窗口。可行性分析文档按本审核 §二 修订后归档为准源。
